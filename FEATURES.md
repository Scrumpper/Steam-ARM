# Steam ARM · native ARM64 Steam client installer

**Feature list** · Steam Frame's ARM64 client · runs on host GPU as ARM program · x86 titles through emulation with graphics forwarded to native drivers, or optional GPU drivers inside emulation · Windows titles through ARM64 Proton · GPU family detection · settings menu `steam-arm-config` · PhysX install step skipped · Remote Play with software decode · controller access rules · uninstaller · one script

---

## Client
- Steam Frame's Steam client: native ARM64 build Valve produced for its ARM based VR headset, Steam Frame, set up on other ARM64 Linux devices (Armv8.0 CPUs: Valve's x86 client through emulation in its place); client interface, input stack, downloader and shader system run on CPU and GPU without emulation; in Linux x86 titles, Steam overlay's in-game part is x86 code loaded into emulated title
- Client package downloads from Valve's stable ARM64 channel on first install and is checked against checksum in Valve's manifest; client's Steam Frame mode switches it to its own ARM update channel on first start, then client restarts itself; sign in from Big Picture or from "Steam ARM (Desktop mode)"
- First start shows desktop notification while client downloads its files without window: download in 10 % steps with total size, unpack, install, then "Steam opens now"; read from client's bootstrap log, sent through `gdbus` (else `notify-send`), updated in place, closed when client exits early; never on later starts
- First start that ends with client files incomplete stops launcher with message to start again (dialog with `zenity` when started from menu); bootstrap exit after its own update gets one more start first
- One client start at once: launcher holds lock (`$XDG_RUNTIME_DIR/steam-arm-start.lock`) through first start, update restarts and normal start until client window process (`steamwebhelper`) runs, at most 180 s after normal start begins; start meanwhile (menu, desktop icon, tray, `steam-arm`) shows notice with first-start progress, replaced in place on each click (`zenity` dialog without notification service, text on terminal), logs it and exits 0; never stops or restarts client
- Launcher warnings that need action (Mali drivers inside emulation missing, private GLX copy missing or broken, display mode not put back, Bluetooth adapter left off, no usable GPU render node, host library `steamwebhelper` cannot load, with its package) also appear as desktop notification when started from menu, once per text per login session; all warnings logged in `steam-arm.log`, capped at 1 MiB at start (one `.1` copy)
- Launcher checks at each start: 16K or 64K page kernel stops start with fix (`STEAM_ARM_IGNORE_PAGESIZE=1` skips; setup keeps it in `/etc/steam-arm/steam-arm.conf`); no GPU render node readable and writable by account gives warning naming group to join
- Installs into desktop user account, not root: account of last run, else first regular account on system (uid 1000), `GAMEUSER` to choose another (root and names with characters other than letters, digits, `.`, `_`, `@` and `-` refused); account is created only when none exists, joins only groups that exist on system, and gets password from `--password-stdin` (never printed or logged) or generated password printed once (no terminal: root-only file `/root/steam-arm-password-<name>.txt`)
- Installer says when account gained `video`, `render`, `input` or `audio` group, so user logs out and back in before first start
- Own home directory under game user's account (`.local/share/steam-arm` by default, `ARMHOME_DIR` in `/etc/steam-arm/steam-arm.conf`, plain relative path checked before use) and own library, so it coexists with x86 client from other routes; run one at time
- `steamos-session-select`, which power menu's Switch to Desktop runs, restarts client in desktop interface
- `--desktop` or `--bigpicture` with client already running stops it as `--shutdown` does and restarts it in that interface
- `steam-arm --shutdown`: asks running client to exit (`steam -shutdown`); client still running 20 s later (x86 client 45 s) gets SIGTERM (client can stop acting on forwarded command lines, for example after second client started under other home folder on same account); never SIGKILL; exit status 1 when client still runs 30 s after SIGTERM
- Display mode restore (X11 session): launcher saves mode and position of each active output when title starts and puts them back once no title runs, so mode title set stays only while it runs (title that quits, crashes or is stopped without restoring it, or restores other refresh rate); same check when Steam closes; logged in `steam-arm.log`; `STEAM_ARM_MODE_RESTORE=0` turns it off; skipped in Wayland sessions and without `xrandr` (host package `x11-xserver-utils`)
- Client that exits after applying its own update (exit status 42, or bootstrap log ending in "Update complete, launching" with no client left running) is started again by launcher, at most twice per start
- `steam-arm --help` lists launcher options, also as root
- Settings menu and tray count only game account's client as running
- `steam-arm` will not run as root (except `--help`); launches Deck interface; `steam-arm --desktop` launches desktop interface, `--bigpicture` forces Deck interface, `STEAM_ARM_UI=desktop` in `/etc/steam-arm/steam-arm.conf` makes desktop default; `STEAM_ARM_HOME` points launcher and tray at another client folder
- `steam-arm-tray`: Steam icon in panel tray with Open Steam, Open in Big Picture, Open in desktop mode, Steam pages (Store, Library, Friends, Downloads, Screenshots and Steam Settings), Stop Steam, Steam ARM Settings, View log and Quit tray, started with session through autostart entry (no desktop filter, so labwc and other desktops that read autostart entries start it too) and by launcher; this client build registers no tray item of its own; Open items greyed while launcher's start lock is held (read from `/proc/locks`), title `Steam (starting)`
- Tray Stop runs `steam-arm --shutdown` (client's own exit, SIGTERM after 20 s, x86 client 45 s, never SIGKILL); Stop greyed while stop runs (offered again after 60 s) and while game of that account runs
- Tray icon: generic icon until client unpacks its files at first start, then client's own tray icon (checked every 3 s) with dark one-pixel outline for light panels, drawn into `$XDG_RUNTIME_DIR/steam-arm-tray/`; without runtime folder, client's icon as is
- Tray Steam pages pass `steam://store`, `steam://open/games`, `steam://open/friends`, `steam://open/downloads`, `steam://open/screenshots` and `steam://open/settings` to running client through `steam-arm --open`; greyed while client is not running, while stop runs and while launcher's start lock is held
- `steam-arm --open URL`: `steam://` link to running client (native client binary, x86 client through emulation); refuses other links, starts no client, does nothing while start lock is held
- Tray Steam ARM Settings opens `steam-arm-config` in terminal emulator through its menu entry, else first of `x-terminal-emulator`, `konsole`, `gnome-terminal`, `xfce4-terminal`, `lxterminal`, `mate-terminal`, `foot`, `alacritty`, `xterm`; View log opens `steam-arm.log` at its end in `less` in first terminal emulator found (else `xdg-open`), greyed while log is missing or empty
- Window rule for KDE: client draws its own frame and asks window manager for none, and this build does not move window when that frame is dragged; rule gives client's normal windows manager's frame so they move and resize like any other window; Big Picture is fullscreen and unaffected; written with `kwriteconfig6` (Plasma 6), else `kwriteconfig5` (Plasma 5); without either on KDE Plasma, setup prints skip line

## Settings menu
- `steam-arm-config` (`/usr/local/bin/steam-arm-config`): menu app for settings after install; built-in full-screen screens (Python `curses`) with textured background and light dialog box, falling back to `dialog`, `whiptail` or plain prompts; `STEAM_ARM_DIALOG=builtin|dialog|whiptail|read` to pick one; `NO_COLOR` honoured; each menu opens with cursor on item chosen last; changes ask for administrator rights through `sudo`; on system without `sudo`, menu says to log in as root (`su -`), then run `steam-arm-config`
- `sudo bash steam-arm-install.sh` in terminal with no options opens it, with that script as its installer; setup writes installer copy to `/usr/local/share/steam-arm/steam-arm-install.sh` for later runs from menu
- Application menu entry "Steam ARM Settings" (`steam-arm-config.desktop`, `Terminal=true`, `TryExec`), written with launcher on every setup run and removed by uninstaller; opens menu in terminal emulator, where `sudo` asks
- Close Steam: screens that need Steam closed (Install / Setup, Components, Controllers, Update / Repair, Uninstall, forced build in Graphics, Remote Play apply, Restore settings) offer `Close Steam`, which runs `steam-arm --shutdown` as game account (Install / Setup: account picked there) and goes on once client has stopped; while game runs (Steam's `reaper SteamLaunch`), asks to quit game first; launcher without `--shutdown` or client still running afterwards: message to close it from its menu or tray; Uninstall stops with message while another account's client runs
- `compat` and `restore` subcommands refuse while Steam ARM runs and name `steam-arm --shutdown` as game account
- Title bar begins with page size state: `pages 4K ok`, `pages 4K (setup kernel switch)`, `pages 16K: reboot for 4K` or `pages 16K: needs 4K`
- Ten sections: Information (system, status, hardware notes); Install / Setup (hardware, page size, Vulkan, parts, account, summary; client download named only when no client is present); Components (parts checklist, driver archive source); Graphics (default route, route per game, forced Linux or Windows build, automatic Windows build, CPU drawing notice; automatic also clears forced build; game lists mark titles drawn on CPU at last start with `CPU!`); Games (overlay, MangoHud, extra environment and arguments, FEX code cache, automatic tuning, "Rules used at last start", remove settings; header names Steam Deck category); Controllers (pads, rules, `pad-xbox`); Remote Play (state, pairing, apply); Maintenance (Update / Repair, logs, hardware report, free `/dev/shm`, back up settings, restore settings, check for new version, caches: FEX code cache sizes, clear all or one game; Steam shader cache size shown, never cleared there; GE-Proton (ARM64), optional; client type; report how last game ran; run history; upgrade to newest release; show what is new; go back to previous version; previous versions kept; check when menu opens); Uninstall (keep games, or remove with games); Help / About (`Fixing a game` page)
- Account step of Install / Setup: list of existing normal accounts (login shell, home folder present; current user and desktop user marked), cursor on current or desktop user; `Create a new account...` entry asks for name and password; no normal account on system opens new-account entry directly
- Settings backup: one file `steam-arm-settings-<date>-<time>.tar.gz` in folder of your choice, mode 600, owned by person who asked; parts picked by checklist: setup choices, system game profiles, personal game profiles, Proton/tool per game (app id and tool name from `config.vdf`), FEX per-game settings (`AppConfig/*.json`), MangoHud settings (`*.conf`), automatic tuning results (`tuned.conf`, `state.json`; as manifest keys, so versions before 3.0 restore every other part); personal parts from account picked in list of existing accounts, stored without account name; no sign-in data, Steam files, accounts or passwords
- Settings restore: archive checked first (manifest and format version, expected names only, no links, no paths outside, size limits); parts checklist of what file holds; personal parts into any existing account; user choices restored, machine state (`GAMEUSER`, `ARMHOME_DIR`, `VERSION`, `FSTAB_ADDED` and others) kept and listed; game profiles merged or replaced, per file, with conflicts decided for all or one by one; tools not installed left out; game with other tool chosen now keeps it (choice made now wins over backup); current files kept as `.bak-restore`; summary (button Next) before Restore / Back; offers `setup --keep` when part lists change; refuses while Steam ARM runs; never creates, changes or deletes accounts, passwords or groups; archive format 1, every later version reads earlier formats
- Subcommands for scripts: `info`, `report` (hardware report without personal details, `~/steam-arm-report.txt`), `report run [APPID|last] [--history] [--save]`, `run-history [on|off]`, `tune <appid> [on|fix|off|reset|show]`, `gfx <appid> auto|a|b`, `gfx-default auto|a|b`, `profile <appid> key=value ...` (`key=` removes one, `--clear` all), `compat <appid> linux|windows|ge|clear`, `auto-build [on|off]`, `cpu-notice [on|off]`, `components a,b,...`, `driver-archive status|download|local FILE|custom FILE SHA256`, `backup [DIR] [--account NAME] [--parts a,b,...]`, `restore FILE [--account NAME] [--parts a,b,...] [--merge|--replace] [--yes]`, `cache [list|clear all|<appid>]` (FEX code cache sizes; clear refused while game runs; Steam shader caches never deleted), `ge-proton [status|check|install|remove]`, `update-check`, `upgrade [--check|--yes|--file ZIP|DEB|--list|--rollback [VERSION]|--allow-older|--snapshot]`, `snapshot-keep [1-5]`, `update-check-on-open [on|off]`, `help fixing`
- Check for new version (Maintenance, or `update-check`, same as `upgrade --check`): by hand only; asks GitHub API `releases/latest` (drafts and pre-releases never listed there), reads version from tag `steam-arm-v<version>`, compares with installed version by version sort, prints release page and upgrade command when newer (package install of release without package asset: package build steps); nothing downloads; 20 s timeout; separate messages for no network, request limit (HTTP 403 or 429), no release (HTTP 404), other HTTP status and unreadable answer; result stored (`/var/lib/steam-arm/release-check`, menu run as user: `~/.cache/steam-arm/release-check`) for main screen line `Steam ARM <version> available` until installed version reaches it
- Upgrade to newest release (Maintenance item shown once newer release found, or `steam-arm-config upgrade`): downloads `Steam.ARM.<version>.zip` and its `.sha256` file over HTTPS only (at most 32 MB, two retries), checks size GitHub lists, sidecar form, SHA-256 against sidecar and GitHub's asset digest, unpacks with path, link, member count (64) and size (16 MB) rules, checks `SA_VERSION` and syntax of its setup, then runs it with `--keep`; free space checked first; same or older release: nothing to do (`--allow-older` permits older with warning; setup before 3.1 has no such option and no snapshot step, so upgrade saves installed version first and runs it without option); package installs: versions compared first; release with package asset `steam-arm-setup_<version>_arm64.deb` (3.1 on): package and `.sha256` downloaded over HTTPS, length, `.sha256` line, GitHub digest (required) and control fields (package, version, arm64) checked before anything runs, plan shown, then setup lock taken, copy of installed version kept, `apt-get install` of checked file (noninteractive, local config files kept, `--allow-downgrades` only with `--allow-older`) and `steam-arm-setup --keep`, restore offered when apt or setup fails; release without package asset: package build steps (downgrade steps with `--allow-older`), nothing downloads; upgrade from zip never writes package files; refused while Steam runs, during another setup run or unfinished change; `--file FILE` for zip, or package on package installs, downloaded by hand with `.sha256` beside it; `--yes` for scripts; log per run in `~/.cache/steam-arm/`; nothing checks, downloads or installs on its own
- Check for new release when menu opens, off by default (`UPDATE_CHECK_ON_OPEN`): at most once daily, 8 s limit, result stored only
- Show what is new: release notes of newest release found by last check
- Rollback protection: setup 3.1 and later saves installed version before each version change to `/var/lib/steam-arm/snapshots/<version>-<date>/` (installer and settings menu copies, `/etc/steam-arm`, every owned program, rule, menu entry and icon with mode and SHA-256, settings backup of that version, SHA-256 manifest); client folder, games, RootFS, Mali and extra Mesa trees and distribution packages never included; snapshot failure stops setup before any change (`--no-snapshot` for full disks); also covers upgrades by hand from 2.3.1 and 3.0
- Go back to previous version (Maintenance, or `upgrade --rollback [VERSION]`): snapshots listed with date, reason, size and check result, damaged ones not selectable, deletable under same lock and protection rules as automatic deletion; current version saved first, chosen snapshot restored, its setup run with `--keep`; failed or interrupted change (`/var/lib/steam-arm/upgrade.state` with no setup running) offered for restore at next menu start and by `upgrade --rollback`, named by next setup run, never restored on its own; change started with `--no-snapshot`: no automatic pick, snapshots listed, version named by hand; package install with newer package: confirmation names package, since Update / Repair in menus before 3.1 runs package command; version changes logged in `/var/lib/steam-arm/history.log`
- Automatic deletion of snapshots after successful upgrade or rollback and on setting change: installed version plus newest snapshot of last 2 earlier versions kept (`SNAPSHOT_KEEP` 1 to 5, Maintenance, Previous versions kept, or `snapshot-keep`); older, damaged and half-written ones deleted with freed space reported, upgrade staging folders of finished or restored changes with them; snapshot of unfinished change and of version before current one never deleted
- Downgrade protection: upgrade never installs older release by itself; setup 3.1 and later over newer install stops before any change unless `--allow-older`; going back through snapshot needs no option
- Update / Repair and other setup runs from menu pick setup script whose version equals installed version (package command, installed copy, file beside menu), else newest of them: older package never runs over newer install
- Hardware report sections beyond system and status: last 20 lines of `steam-arm.log`, start, update and error lines of client's `logs/bootstrap_log.txt`, closing block of newest setup log of account running menu, groups of game account next to groups of its oldest running process with `Not active yet` list; whole report through same filter for home folders, account and full names, host name, Steam sign-in and persona names, Steam IDs, IPv4 and IPv6 addresses, MAC and e-mail addresses and token values; line still holding account, host or sign-in name after that dropped
- Run report (Maintenance, Report how last game ran; `report run [APPID|last] [--history] [--save]`): one game start, last started or picked; summary (App ID, game name, route, graphics route, renderer verdict, result: run time and exit status of launch chain, still running, or end without record), upstream fields of FEX, Proton and Steam client issue forms, settings in effect from launch handler lines, kernel GPU, memory and crash lines of run window, core dump signal and frames of game or FEX programs (`systemd-coredump`), `/dev/shm`, `vm.max_map_count`, free memory, hottest thermal zone, earlier starts of same game (other games' App IDs only with `--history` or ticked), folded handler lines, error lines of Valve's FEX tool log (environment lines left out) and hardware report; reads only allow-listed lines, never `steam.token`, `ssfn*` or `userdata/`; hardware report filter plus machine-id, board serial, MAC addresses and Wi-Fi name, line still holding such value or Steam ID dropped, no report when Steam sign-in file cannot be read; shown before saving (menu screen, terminal pager), `~/steam-arm-report-<appid>-<YYYYMMDD>-<HHMM>.md` mode 600, 30 KB cap (oldest log lines out first); Windows games on ARM64 Proton and native games: route, Steam start and end, hardware, `run record: not available for this route`
- Automatic tuning (title key `autotune=fix`, off unless set; Games, game, Automatic tuning; `tune <appid> [on|fix|off|reset|show]`): x86 Linux titles through emulation; verdict per start from time, CPU use and renderer check (crash: chain ended within 60 s before GPU memory; hang: under 0.02 s CPU per s for 90 s before GPU memory, cleared when game holds GPU memory later in same start (own launcher window waited for input); CPU drawing; no graphics in 300 s; exit status not used, chain returns 0 after crash); after bad verdict next start tries one changed setting from best found so far (`gfx` flip where route B exists, `multiblock` flip, `gl32=off` for 32-bit titles on forwarding route), good start keeps it; at most 4 trials per stamp (FEX tool, game build, Mesa, GPU family, client type); never TSO, x87 or SMC settings; results in client home `.config/steam-arm/tuned.conf` (title profile syntax with evidence, loaded below `/etc` and personal profiles, so keys set there win and are never tried), state in `autotune/state.json` (owner only); key removed from `tuned.conf` by hand never tried again; `tuned.conf` line with tuning evidence but no decision state (restored backup) counts as tuning result; off keeps results and drops pending trial, reset deletes them; never signals game, hang gives one desktop notice to use Steam's Stop; at most one tuning notice per start; turns run history on for that title
- Run history (`RUN_HISTORY`, off unless set `on`; Maintenance, Run history; `run-history [on|off]`): one `key=value` line per start (launch handler) and per end (launch wrapper stand-in: exit status or signal, run time, renderer verdict) in client folder `.local/state/steam-arm/runs.log`; values only (no paths, names or profile values); newest 200 lines; owner only, never written through link; not in settings backups; off deletes it; x86 games through emulation only
- View logs: empty launcher log says `launcher writes warnings only`; empty game or setup log says `is empty`; log of another account not readable without `sudo` says so; Last setup run in menu run by desktop account names administrator's log folder and `sudo steam-arm-config`
- Information shows host OpenGL renderer and versions (`glxinfo -B`) and CPU governor with max clock per CPU cluster (cpufreq policy), `mixed` when clusters use different governors; host renderer on CPU gives note `GPU forwarding not active: rendering on CPU (llvmpipe)`; row `Vulkan gaps` lists features `vk-spoof` reports that Vulkan driver lacks
- `Fixing a game` page: launch options that work, with examples; slow game (renderer line, resolution test, per-core load); Proton choice that changes back; what to avoid (MangoHud on Proton ARM64 titles, options for NVIDIA or AMD cards, package installs inside emulation); what cannot be fixed (Direct3D 12, Unreal Engine 4 and 5, kernel anti-cheat); how to read "Rules used at last start"

## GPU detection
- GPU family from kernel driver name of each render node (DRM version query), Mali GPU id (Panthor and Panfrost queries), device tree compatible string and PCI vendor; highest ranked node wins, so discrete card wins over integrated GPU; `/dev/mali0` without render node read as Arm's closed `kbase` driver
- 29 GPU families (Mali, Adreno, Apple, Raspberry Pi, Vivante, PowerVR, AMD, NVIDIA, Intel, virtual GPU), plus `none` and `unknown`; each sets default state of `vk-spoof`, `gpu-in-emulation` and `glx-lax`, with note or warning printed at install
- Mali components on by default on Mali GPUs: `vk-spoof` on Mali-G610 class (`mali-csf-v10`), `gpu-in-emulation` on it, on Mali-G615/G715 (`mali-csf-v11`), on Mali 5th gen and on Panfrost Malis; off on other GPUs, on Mali-G1 (`mali-csf-g1`, needs Mesa 26.2), on Panthor Malis outside family table, on Mali-400/450 and on closed `kbase` driver
- Vulkan driver and device name from `vulkaninfo` when installed; GPU line printed by installer, checklist and `--detect`
- `--detect`: GPU family, detected family, GPU, kernel driver, Vulkan driver, Vulkan features native and missing, published driver archive (file, SHA-256), CPU cores with Armv8 level, client type, FEX tool type and handler entry, extra Mesa versions (`mesa extra:`), signs of official ARM64 Linux client from Valve (`official client: none|found (...)`: arm64 package owning `/usr/bin/steam`, Steam folder with ARM64 client parts and no Steam ARM mark, running client started without `-deckard`; detection only, also in hardware report), one `patch <name>: active|retired|off (reason)` line per own fix (`thunk-paths`, `tool-edit`, `server-socket`, `code-cache`, `glx-lax`, `vk-spoof`, `x86-client`, `guestos-link`), page size, distribution, default state of each component, note or warning; one `key: value` per line; installs nothing, needs no root
- `GPU_FAMILY=id` picks family by hand and is kept for later runs (`GPU_FAMILY_SET=user`); `GPU_FAMILY=auto` detects again; unknown id stops install with list of valid ones, and with `--detect` prints warning and valid ones, then detected family, exit status 0
- Launch handler reads same family: Mali drivers route only on Mali families (not `mali-csf-g1`); 32-bit Vulkan titles on it only on `mali-csf-v10`, since PanVK loads by default only there

## Games
- x86 Linux titles run through emulation tool client downloads, against x86-64 Ubuntu 24.04 root filesystem installer prepares at `/opt/fex-rootfs`
- Windows titles run through ARM64 Proton build client downloads; Direct3D through DXVK, feature level 10_1 on Mali
- `shader-cache` component, off by default on every GPU family: Steam's shader pre-caching, so Windows titles play in-game videos in place of colour bars; launcher starts client without `-noshaders` and sets `DISABLE_VK_LAYER_VALVE_steam_fossilize_1=1` for games through game environment file (Steam's ARM64 pipeline caching layer stops Proton titles at Vulkan device creation); costs several GB of download into `steamapps/shadercache` and processing on all cores after first start, installs and updates; turning it off keeps cache, and turning it on again reuses it; settings menu shows cache size per library when part is turned off; deleting `steamapps/shadercache` by hand stops Steam from downloading those caches again
- PhysX install step: launcher reads each Proton title's install script and writes step's has-run value (at least 1, never below script's minimum) into title's prefix, only while no Wine process uses it, so Steam skips legacy PhysX installer that hangs under emulation; before prefix exists, PhysX installer running over 60 seconds gets SIGTERM and Steam continues to title; logged in `steam-arm.log`; component `physx-skip`, on by default on every GPU family, off stops launcher step and removes no files; `STEAM_ARM_PHYSX_SKIP=0` or `=1` turns it off or on for one client session
- `steam-arm-compatmap <appid> <tool>`: pins title to compatibility tool in client's stored configuration, for title with Linux build on record but Windows files installed; tool `steamlinuxruntime` switches title to its Linux build, `proton_11-arm64` to Windows build; `--remove` deletes title's entry, and Steam picks build again; `steam-arm-config compat` and Graphics > Route per game run it; refuses while Steam ARM runs, and refuses non-numeric app id, tool name with characters other than letters, digits, `_`, `.` and `-`, and malformed `config.vdf` (file unchanged); first original kept as `config.vdf.bak-steam-arm`, never overwritten
- MangoHud in x86 Linux titles: `mangohud %command%`, `MANGOHUD=1 %command%` or profile `mangohud=on`; launch handler copies root filesystem's MangoHud library into client folder (`.local/lib/steam-arm`, refreshed when root filesystem copy changes) and loads it from there, since game container maps `/usr` libraries to host system, which has no x86 build; 64-bit titles only (root filesystem has no 32-bit MangoHud); host without MangoHud gets shim `/usr/local/bin/mangohud` that sets `MANGOHUD=1` for handler (`mangohud` of MangoHud package never replaced, removal deletes only shim)
- Renderer check: once title loads OpenGL or Vulkan library, launch handler logs GPU device its processes use, counted once GPU memory is allocated on it (`renderer: GPU (<driver> <node>), forwarding to host driver`, or `drivers inside emulation` on Mali drivers route), or after 30 s without one while title process stays busy (0.1 s CPU per s or more over last 30 s and last 10 s) `renderer: warning: GPU forwarding not active: rendering on CPU (llvmpipe)` with reason (x86 Mesa inside emulation loaded, or no GPU device in use); idle title without GPU memory (loading, waiting for input, stuck) gets no CPU verdict, and check that ends without verdict logs `renderer: not detected` naming idle process; runs in background for up to 180 s, game start not delayed; `STEAM_ARM_RENDERER_CHECK=0` turns it off per title; hardware report lists renderer lines of five newest starts
- CPU drawing notice (`CPU_NOTICE`, off unless set `on`): CPU verdict of renderer check raises desktop notice in game account's session (`gdbus`, else `notify-send`; urgency critical, stays until closed); GoldSrc titles excluded; x86 titles only (launch handler path); `steam-arm-config cpu-notice [on|off]`, Graphics menu; `CPU_NOTICE` in settings backup
- Frame pacing readout (`steam-arm --perf-stats` or `STEAM_ARM_PERF_STATS=1`, off by default): every 5 s per frame source frame count, interval p50, p95, p99 and maximum in ms (nearest rank), intervals over 25 ms and over 50 ms, on terminal and in client home `.local/state/steam-arm/perf.log` (newest 200); hardware report lists last 12; frame times from Mesa overlay layer (`VK_LAYER_MESA_overlay`, `no_display`, Vulkan) and Gallium HUD dump (`GALLIUM_HUD=frametime`, hidden, OpenGL) set through game environment file only while on; with Steam running, covers games started from then on until Ctrl+C
- Still-working notice (`STILL_NOTICE`, auto unless set `on` or `off`; Graphics menu; `steam-arm-config still-notice [on|off|auto]`): game with no frame 20 s after start (`STEAM_ARM_STILL_AFTER`) gets one desktop notice (terminal line without notice service) naming compiling shaders (shader cache growth, `fossilize_replay`), loading, or not responding (under 0.1 s CPU in 10 s, or disk wait with no reads); replaced as state changes, closed on first frame; frame signal from GPU engine time or cycles in kernel `fdinfo` or readout files; notice needs kernel that reports per-process GPU time, otherwise stays silent (readout files still count when readout is on); auto runs only where display mode restore looks for games each second already (no added work while idle); never signals game; `STILL_NOTICE` in settings backup

## Graphics

- FEX `Multiblock` on in game user's own FEX configuration, which x86 Remote Play client uses; titles run through Valve's FEX tool, which builds its configuration from its own template and Valve's per-title setting; profile key `multiblock=on|off` sets it per title (launch-option `FEX_APP_CONFIG` and Steam's FEX setting win); FEX logging off in Valve's FEX tool configuration
- Profile key `diskcache=on|off`: FEX code cache per title through `FEX_APP_CONFIG` (`DiskCache`), only with Valve FEX tool FEX-2609.1 or newer (older tool: log line, nothing written); off unless set; covers every emulated process of title start, runtime helper scripts included (2 of 11 starts with empty cache hung in runtime helper on test device); titles with own JIT compiler (Java, Mono, .NET, LuaJIT, CEF) cache file-backed code only (`DiskCacheAnonCaching` 0); launch option `FEX_DISKCACHE` or `FEX_APP_CONFIG` with `DiskCache` wins, Steam's FEX setting does not block it; title cache deleted once before start after FEX tool or game build change (stamp file in title's cache folder; linked folder left alone); Valve FEX tool FEX-2610 or newer turns code cache on for every title itself (1 GB cap, entries of older FEX versions pruned): `diskcache=on` adds nothing, cache deleted only after game build change, `diskcache=off` turns it off per title; hardware report line counts titles with it on and total cache size

## Remote Play
- Streaming runs package's x86-64 streaming client under system emulator, with software decoding; native ARM64 streaming client hardware path (V4L2) fails with green screen on Qualcomm Iris (steam-for-linux #13428) and has no V4L2 decoder to use on Rockchip
- `steam-arm-remoteplay` pins hardware decoding off and HEVC off in client's stored configuration, so host keeps to H.264 and software decoder; x86-64 streaming client under emulation reaches no host video decoder, and with hardware decoding advertised session can hang on launch screen and never finish negotiating
- Launcher applies setting before every client start once account has signed in, so first stream already runs with it; `--check` reports without changing anything; Remote Play section of `steam-arm-config` shows state and applies it
- Game window in background on host renders nothing new, so stream shows one frame and takes no input; keep game in foreground on host

## Controllers
- `pad-hidraw` component: Valve's controller rules from `steam-devices` (`/etc/udev/rules.d/60-steam-input.rules`), unless system package already provides them; plus `/etc/udev/rules.d/60-steam-arm-gamepad-hidraw.rules` for 241 pads from kernel `xpad` table that Valve's list lacks, matched on vendor and product; Sony and Nintendo hidraw devices matched by kernel pad driver (`hid-playstation`, `hid-sony`, `hid-nintendo`), so keyboards and mice of those makers stay out, with whole vendor as fallback on kernel without that driver module; client reads pads directly for rumble and battery level
- `xpad-dedup` component: `/etc/udev/rules.d/71-steam-arm-xpad-dedup.rules` unbinds driver from headset interface some third-party Xbox 360 style pads expose, so one pad is one joystick and two-player game does not hand player 2 copy of player 1; `steam-arm-xpad-dedup` does same for pads already connected
- `pad-xbox` component, off by default: `steam-arm-pad-xbox.service` presents XInput pads from other makers as Xbox 360 pads through `uinput`; off because client's own Steam Input re-identifies pads, and launcher pauses service while client runs, through sudo rule that exists only with this component and is checked with `visudo` before it goes live

- Header names no board; same script runs on its own or from units, TTY gated, `NO_COLOR` honoured
- Security: files in game account's home written as that account; client folder path validated; account named in settings file must exist; Valve's FEX tool files, settings, profiles and `config.txt` edited through new file renamed over old one; temporary files made with `mktemp` and removed on exit; client package and driver archive checked against checksums
- Uninstaller: `--remove` removes launcher, helpers, settings menu, installer copy, menu and desktop entries, icons, controller rules, services, sudo rule, window rule, apt hook, setup logs, snapshots and records of version changes (`/var/lib/steam-arm`), upgrade downloads (`/var/cache/steam-arm`) and `/etc/steam-arm` (game profiles saved to `/var/backups/steam-arm-titles-<date>.conf` first), and restores `vm.max_map_count`, root filesystem's Mesa files and package tools, Raspberry Pi `config.txt` (backup then deleted), Steam launch options without part Raspberry Pi GPU title settings added, KDE input permission (when `kde-input-prompt` set it), Valve's FEX tool files and Valve's streaming client; turns lingering off only when setup turned it on; removes `graphics_provider.json` and `~/.fex-emu/Config.json` only while unchanged after setup; removes `/dev/shm` line from `/etc/fstab` only when setup added it; retains client folder with games unless deletion is confirmed by typing `DELETE`, and deletes it only when it holds marker `.steam-arm-client` (older install without marker: folder kept, `rm -rf` line printed); keeps root filesystem, distribution packages, account groups, `/dev/shm` line setup did not add (listed as kept) and account setup created (prints `sudo userdel -r <name>`), and prints `apt remove` line for packages nothing else needs; refuses while client runs or another setup run is in progress
- `--replace-other`: retires other variant of this installer before setup into two archives: system files to `/var/backups/steam-arm-replaced-<date>.tar`, files from its account's home to `/var/backups/steam-arm-replaced-<date>-<user>.tar`, owned by that account; restore commands printed (`sudo tar -xpf <archive> -C /`, `sudo -u <user> tar -xpf <archive> -C /`); client folder and account of other variant stay in use unless `ARMHOME_DIR`, `GAMEUSER` or settings file name others
- `--detect-other`: prints whether other variant of this installer is present, status 0 when present; needs no root. Install in `steam-arm-config` asks before it replaces other variant (Replace or Back)
- `--remove --purge`: also deletes client folder with every installed game (marker required) and root filesystem, after typed confirmation; root filesystem only when setup downloaded it and other variant of this installer is not installed; without terminal nothing is deleted

## Requirements
- ARM64 system; Vulkan driver for Windows titles, native OpenGL titles run without one; Debian or Ubuntu family distribution, since installer uses `apt`
- Ubuntu 25.10 or newer, Debian 13 or newer, or distribution built on them (SDL3 packages); host package check with `apt-cache policy` halts setup before any package or package source change and names missing packages
- Mesa graphics stack for `glx-lax`; `vk-spoof` and `gpu-in-emulation` written for Mali (Panfrost and PanVK), on by default on Mali GPUs only
- FEX PPA: added with `add-apt-repository` on Ubuntu family, as apt source with fingerprint-checked key on Debian 13 and Raspberry Pi OS built on it; Debian 12 and older stop at host package check (no SDL3 packages)
- FEX from another source (`FEX` command not owned by `fex-emu` package, x86 binfmt entries registered): no FEX packages installed; thunk folders from FEX's own prefix, `/usr` or `/usr/local`, else GL and Vulkan thunks off in game user's FEX configuration with warning; missing binfmt entries halt setup before any change
- No hardcoded GPU render node or card index; GPU family detection reads every render node
