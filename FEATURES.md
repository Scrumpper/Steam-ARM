# Steam ARM · native ARM64 Steam client installer

**Feature list** · Steam Frame's ARM64 client · runs on host GPU as ARM program · x86 titles through emulation with graphics forwarded to native drivers, or optional GPU drivers inside emulation · Windows titles through ARM64 Proton · GPU family detection · settings menu `steam-arm-config` · PhysX install step skipped · Remote Play with software decode · controller access rules · uninstaller · one script

---

## Client
- Native ARM64 build of Steam client, build Valve produced for its ARM based VR headset, Steam Frame; client interface, input stack, downloader and shader system run on CPU and GPU without emulation; in Linux x86 titles, Steam overlay's in-game part is x86 code loaded into emulated title
- Client package downloads from Valve's stable ARM64 channel on first install and is checked against checksum in Valve's manifest; client's Steam Frame mode moves it to its own ARM update channel on first start, then client restarts itself; sign in from Big Picture or from "Steam ARM (Desktop mode)"
- First start shows desktop notification while client downloads its files without window: download in 10 % steps with total size, unpack, install, then "Steam opens now"; read from client's bootstrap log, sent through `gdbus` (else `notify-send`), updated in place, closed when client exits early; never on later starts
- Installs into desktop user account, not root: account of last run, else first regular account on system (uid 1000), `GAMEUSER` to choose another (root and names with characters other than letters, digits, `.`, `_`, `@` and `-` refused); account is created only when none exists, joins only groups that exist on system, and gets password from `--password-stdin` (never printed or logged) or generated password printed once (no terminal: root-only file `/root/steam-arm-password-<name>.txt`)
- Installer says when account gained `video`, `render`, `input` or `audio` group, so user logs out and back in before first start
- Own home directory under game user's account (`.local/share/steam-arm` by default, `ARMHOME_DIR` in `/etc/steam-arm/steam-arm.conf`, plain relative path checked before use) and own library, so it coexists with x86 client from other routes; run one at time
- `steamos-session-select`, which power menu's Switch to Desktop runs, restarts client in desktop interface
- `--desktop` or `--bigpicture` with client already running stops it as `--shutdown` does and restarts it in that interface
- `steam-arm --shutdown`: asks running client to exit (`steam -shutdown`); client still running 20 s later gets SIGTERM (client can stop acting on forwarded command lines, for example after second client started under other home folder on same account); never SIGKILL; exit status 1 when client still runs 30 s after SIGTERM
- Display mode restore (X11 session): launcher saves mode and position of each active output when title starts and puts them back once no title runs, so mode title set stays only while it runs (title that quits, crashes or is stopped without restoring it, or restores other refresh rate); same check when Steam closes; logged in `steam-arm.log`; `STEAM_ARM_MODE_RESTORE=0` turns it off; skipped in Wayland sessions and without `xrandr` (host package `x11-xserver-utils`)
- Client that exits after applying its own update (exit status 42, or bootstrap log ending in "Update complete, launching" with no client left running) is started again by launcher, at most twice per start
- `steam-arm` refuses to run as root; launches Deck interface; `steam-arm --desktop` launches desktop interface, `--bigpicture` forces Deck interface, `STEAM_ARM_UI=desktop` in `/etc/steam-arm/steam-arm.conf` makes desktop default; `STEAM_ARM_HOME` points launcher and tray at another client folder
- `steam-arm-tray`: Steam icon in panel tray with Open, Open in desktop mode, Stop and Quit, started with session through autostart entry and by launcher; this client build registers no tray item of its own
- Window rule for KDE: client draws its own frame and asks window manager for none, and this build does not move window when that frame is dragged; rule gives client's normal windows manager's frame so they move and resize like any other window; Big Picture is fullscreen and unaffected

## Settings menu
- `steam-arm-config` (`/usr/local/bin/steam-arm-config`): menu app for settings after install; built-in full-screen screens (Python `curses`) with textured background and light dialog box, falling back to `dialog`, `whiptail` or plain prompts; `STEAM_ARM_DIALOG=builtin|dialog|whiptail|read` to pick one; `NO_COLOR` honoured; each menu opens with cursor on item chosen last; changes ask for administrator rights through `sudo`; on system without `sudo`, menu says to log in as root (`su -`), then run `steam-arm-config`
- `sudo bash steam-arm-install.sh` in terminal with no options opens it, with that script as its installer; setup writes installer copy to `/usr/local/share/steam-arm/steam-arm-install.sh` for later runs from menu
- Title bar starts with page size state: `pages 4K ok`, `pages 4K (setup kernel switch)`, `pages 16K: reboot for 4K` or `pages 16K: needs 4K`
- Ten sections: Information (system, status, hardware notes); Install / Setup (hardware, page size, Vulkan, parts, account, summary; client download named only when no client is present); Components; Graphics (default route, route per game, forced Linux or Windows build; automatic also clears forced build); Games (overlay, MangoHud, extra environment and arguments, "Rules used at last start", remove settings); Controllers (pads, rules, `pad-xbox`); Remote Play (state, pairing, apply); Maintenance (Update / Repair, logs, hardware report, free `/dev/shm`, back up settings, restore settings); Uninstall (keep games, or remove with games); Help / About (`Fixing a game` page)
- Account step of Install / Setup: list of existing normal accounts (login shell, home folder present; current user and desktop user marked), cursor on current or desktop user; `Create a new account...` entry asks for name and password; no normal account on system opens new-account entry directly
- Settings backup: one file `steam-arm-settings-<date>-<time>.tar.gz` in folder of your choice, mode 600, owned by person who asked; parts picked by checklist: setup choices, system game profiles, personal game profiles, Proton/tool per game (app id and tool name from `config.vdf`), FEX per-game settings (`AppConfig/*.json`), MangoHud settings (`*.conf`); personal parts from account picked in list of existing accounts, stored without account name; no sign-in data, Steam files, accounts or passwords
- Settings restore: archive checked first (manifest and format version, expected names only, no links, no paths outside, size limits); parts checklist of what file holds; personal parts into any existing account; user choices restored, machine state (`GAMEUSER`, `ARMHOME_DIR`, `VERSION`, `FSTAB_ADDED` and others) kept and listed; game profiles merged or replaced, per file, with conflicts decided for all or one by one; tools not installed left out; game with other tool chosen now keeps it (choice made now wins over backup); current files kept as `.bak-restore`; summary (button Next) before Restore / Back; offers `setup --keep` when part lists change; refuses while Steam ARM runs; never creates, changes or deletes accounts, passwords or groups; archive format 1, every later version reads earlier formats
- Subcommands for scripts: `info`, `report` (hardware report without personal details, `~/steam-arm-report.txt`), `gfx <appid> auto|a|b`, `gfx-default auto|a|b`, `profile <appid> key=value ...` (`key=` removes one, `--clear` all), `compat <appid> linux|windows|clear`, `components a,b,...`, `backup [DIR] [--account NAME] [--parts a,b,...]`, `restore FILE [--account NAME] [--parts a,b,...] [--merge|--replace] [--yes]`, `help fixing`
- Information shows host OpenGL renderer and versions (`glxinfo -B`) and CPU governor with max clock per CPU cluster (cpufreq policy), `mixed` when clusters use different governors; host renderer on CPU gives note `GPU forwarding not active: rendering on CPU (llvmpipe)`
- `Fixing a game` page: launch options that work, with examples; slow game (renderer line, resolution test, per-core load); Proton choice that changes back; what to avoid (MangoHud on Proton ARM64 titles, options for NVIDIA or AMD cards, package installs inside emulation); what cannot be fixed (Direct3D 12, Unreal Engine 4 and 5, kernel anti-cheat); how to read "Rules used at last start"

## GPU detection
- GPU family from kernel driver name of each render node (DRM version query), Mali GPU id (Panthor and Panfrost queries), device tree compatible string and PCI vendor; highest ranked node wins, so discrete card wins over integrated GPU; `/dev/mali0` without render node read as Arm's closed `kbase` driver
- 27 GPU families (Mali, Adreno, Apple, Raspberry Pi, Vivante, PowerVR, AMD, NVIDIA, Intel, virtual GPU), plus `none` and `unknown`; each sets default state of `vk-spoof`, `gpu-in-emulation` and `glx-lax`, with note or warning printed at install
- Mali components on by default on Mali GPUs: `vk-spoof` on Mali-G610 class (`mali-csf-v10`) and Mali 5th gen, `gpu-in-emulation` on those and on Panfrost Malis; off on other GPUs, on Panthor Malis Mesa does not support yet, on Mali-400/450 and on closed `kbase` driver
- Vulkan driver and device name from `vulkaninfo` when installed; GPU line printed by installer, checklist and `--detect`
- `--detect`: GPU family, detected family, GPU, kernel driver, Vulkan driver, page size, distribution, default state of each component, note or warning; one `key: value` per line; installs nothing, needs no root
- `GPU_FAMILY=id` picks family by hand and is kept for later runs (`GPU_FAMILY_SET=user`); `GPU_FAMILY=auto` detects again; unknown id stops install with list of valid ones, and with `--detect` prints warning and valid ones, then detected family, exit status 0
- Launch handler reads same family: Mali drivers route only on Mali families; 32-bit Vulkan titles on it only on `mali-csf-v10` and `mali-csf-5thgen`

## Games
- x86 Linux titles run through emulation tool client downloads, against x86-64 Ubuntu 24.04 root filesystem installer prepares at `/opt/fex-rootfs`
- Windows titles run through ARM64 Proton build client downloads; Direct3D through DXVK, feature level 10_1 on Mali
- `shader-cache` component, off by default on every GPU family: Steam's shader pre-caching, so Windows titles play in-game videos in place of colour bars; launcher starts client without `-noshaders` and sets `DISABLE_VK_LAYER_VALVE_steam_fossilize_1=1` (Steam's ARM64 pipeline caching layer stops Proton titles at Vulkan device creation); costs several GB of download into `steamapps/shadercache` and processing on all cores after first start, installs and updates; turning it off keeps cache, and turning it on again reuses it; settings menu shows cache size per library when part is turned off; deleting `steamapps/shadercache` by hand stops Steam from downloading those caches again
- PhysX install step: launcher reads each Proton title's install script and writes step's has-run value (at least 1, never below script's minimum) into title's prefix, only while no Wine process uses it, so Steam skips legacy PhysX installer that hangs under emulation; before prefix exists, PhysX installer running over 60 seconds gets SIGTERM and Steam continues to title; logged in `steam-arm.log`; component `physx-skip`, on by default on every GPU family, off stops launcher step and removes no files; `STEAM_ARM_PHYSX_SKIP=0` or `=1` turns it off or on for one client session
- `steam-arm-compatmap <appid> <tool>`: pins title to compatibility tool in client's stored configuration, for title with Linux build on record but Windows files installed; tool `steamlinuxruntime` switches title to its Linux build, `proton-stable-arm64` to Windows build; `--remove` deletes title's entry, and Steam picks build again; `steam-arm-config compat` and Graphics > Route per game run it; refuses while Steam ARM runs, and refuses non-numeric app id, tool name with characters other than letters, digits, `_`, `.` and `-`, and malformed `config.vdf` (file unchanged); first original kept as `config.vdf.bak-steam-arm`, never overwritten
- MangoHud in x86 Linux titles: `mangohud %command%`, `MANGOHUD=1 %command%` or profile `mangohud=on`; launch handler copies root filesystem's MangoHud library into client folder (`.local/lib/steam-arm`, refreshed when root filesystem copy changes) and loads it from there, since game container maps `/usr` libraries to host system, which has no x86 build; 64-bit titles only (root filesystem has no 32-bit MangoHud)
- Renderer check: once title loads OpenGL or Vulkan library, launch handler logs GPU device its processes use, counted once GPU memory is allocated on it (`renderer: GPU (<driver> <node>), forwarding to host driver`, or `drivers inside emulation` on Mali drivers route), or after 30 s without one `renderer: warning: GPU forwarding not active: rendering on CPU (llvmpipe)` with reason (x86 Mesa inside emulation loaded, or no GPU device in use); runs in background for up to 180 s, game start not delayed; `STEAM_ARM_RENDERER_CHECK=0` turns it off per title; hardware report lists renderer lines of five newest starts
- Compatibility tool check: launch handler reads title's entry in Steam's `config.vdf`; Proton build saved there while Linux build starts gives `compat: warning` line; x86 Proton through emulation gives `compat: x86 Proton` line; handler never writes `config.vdf`
- GoldSrc titles (Half-Life engine): log line notes that video options pick OpenGL or Software renderer, and Software draws on CPU
- Launch handler logs values it leaves alone: `launch option kept: NAME=value (rule wanted ...)`, `title setting kept: gfx=...`; Unity and Godot lines name values in effect, launch options included (renderer, reported GL version)
- Mali drivers route: FEX `Multiblock` from `FEX_APP_CONFIG` launch option kept (`launch option kept`), Steam's per-title FEX setting counts as default, not user choice; GL or Vulkan thunk, graphics provider and GLX vendor from launch options replaced (`overridden for Mali route`); profile `gl32=off` sets GLX vendor `mesa`
- Package-install guard: `apt`, `apt-get` and `dpkg` of x86 root filesystem refuse and change nothing, since package installs under FEX write to host system; read-only `dpkg` queries still answer; originals kept as `<tool>.steam-arm-real` for experts and put back by `--remove`
- Titles protected by kernel-level anti-cheat do not run: anti-cheat and DRM components require system call filter emulator does not implement

## Graphics
- Forwarding route, default for most titles: OpenGL and Vulkan calls from emulated guest forwarded to host's native Mesa libraries through FEX thunks, not emulated; host thunks at `/usr/lib/aarch64-linux-gnu/fex-emu/HostThunks`, guest thunks at `/usr/share/fex-emu/GuestThunks`, root filesystem linked as `/usr/share/guestos/fex-mesa`
- Valve's FEX tool 2609 and later lists runtime container library paths for forwarding itself; launcher edits its `ThunksDB.json` only for older tools
- FEX `Multiblock` on in game user's own FEX configuration, which x86 Remote Play client uses; titles run through Valve's FEX tool, which builds its configuration from its own template and Valve's per-title setting; profile key `multiblock=on|off` sets it per title (launch-option `FEX_APP_CONFIG` and Steam's FEX setting win); FEX logging off in Valve's FEX tool configuration
- Valve's FEX tool edited only once its files stay unchanged for about 2 s after Steam updates it; each edited file gets `<file>.steam-arm-sha` record of bytes written, removed with original copy `<file>.steam-arm-orig` when uninstall puts Valve's files back
- 32-bit titles on forwarding: OpenGL forwarded, Vulkan not (FEX forwards Vulkan for 64-bit code only); there launch handler removes `-vulkan` and `-force-vulkan` from them, profile key `vk32=keep` keeps it
- Profile key `gl32=off`: title not detected as 64-bit, without OpenGL forwarding, on x86 Mesa inside emulation, through FEX app configuration (`ThunksDB` GL off) merged with Steam's FEX settings
- `gpu-in-emulation` component, on by default on Mali GPUs: x86-64 and i386 Mesa 26.1.8 with Panfrost and PanVK in second graphics tree `/opt/fex-rootfs/Ubuntu_24_04-mali`, hard-link copy of root filesystem (about 330 MB extra disk), same layout Valve uses on Steam Frame; root filesystem used for forwarding unchanged; archive `steam-arm-fex-mesa-26.1.8-x86_64-i386.tar.zst` (about 75 MB) from project release, SHA-256 checked; download from release address, then same file name under `releases/latest/download`; HTTP 404 at both stops setup with message naming missing file and `STEAM_ARM_PROVIDER_TARBALL`; `STEAM_ARM_PROVIDER_TARBALL` for local file in place of download; second tree deleted when component is deselected or removed; Windows titles unaffected
- Graphics route per title, automatic: launch handler puts Java titles (bundled Java runtime detected in game folder) and, on `mali-csf-v10` and `mali-csf-5thgen`, 32-bit titles started with `-vulkan` or `-force-vulkan` (option kept) on Mali drivers in emulation, every other title on forwarding; LWJGL 2 titles get `-DLWJGL_DISABLE_XRANDR=true`, Java 21 and newer get FEX Multiblock off unless `FEX_APP_CONFIG` launch option sets it; profile key `gfx=a|b` overrides per title, `gfx=b` on non-Mali GPU with published archive: forwarding and warning; game log line `steam-arm: graphics:` names route and reason
- Settings menu offers route B, default and per game, on Mali GPU or with custom driver tree only; elsewhere it notes that route B needs Mali GPU or custom driver archive, shows earlier B setting as `b (not used on this GPU)` and `steam-arm-config` refuses `b`; B on Mali GPU without `gpu-in-emulation` comes with note that games use forwarding until it is installed
- Settings menu Games section: Windows titles (Proton in Steam's compatibility tool list, Windows build installed, or Proton prefix in `compatdata`) show rules and remove-all only, with note to use Steam launch options
- Settings menu status: custom driver tree shown as `present (custom drivers, sha <first 12>…)`
- Settings menu sudo prompt: cleared screen, heading `Administrator password for <user> (sudo):`, prompt on next line, menu back afterwards
- Downloads: curl progress bar on terminal only; setup logs and menu screens get error lines only
- `GFX_DEFAULT` in `/etc/steam-arm/steam-arm.conf`: `auto` (default; empty same) rules decide, `a` (`forward` reads same) every title on forwarding, `b` every title on Mali drivers (Mali GPU, or any GPU with custom driver archive); other values: rules, with log line; `steam-arm-config gfx-default auto|a|b` and Graphics menu write same values
- Custom driver archive, for advanced users: `STEAM_ARM_PROVIDER_TARBALL=/path` plus `STEAM_ARM_PROVIDER_SHA256=<sha>`; SHA-256 and layout checked (only `usr/`, `etc/`, `graphics_provider.json` at top, Mesa driver library present), warning printed; kept across repair and update, `--provider-default` switches back; `gfx=b` and `GFX_DEFAULT=b` apply on any GPU with it, automatic rules stay Mali-only; results depend on Mesa and kernel versions
- Driver archive recipe `tools/build-driver-archive.sh` in GitHub source: x86-64 Linux PC, about 25 GB disk, network, no root (user namespaces); writes `.tar.zst` and `.sha256`; GitHub Actions workflow "Build driver archive" runs it from fork with Mesa version as input
- `glx-lax` component: private copy of Mesa GLX client library, `libGLX_steamarmlax.so.0`, with one check relaxed, for titles that bind single OpenGL context from more than one thread; own library name through `patchelf` so system copy is untouched; apt hook rebuilds it after every package run that changed system Mesa GLX; launcher uses system GLX with log message when copy is missing or cannot load; used on forwarding route (Mali drivers in emulation carry same check relaxed)
- `vk-spoof` component: implicit Vulkan layer `VK_LAYER_STEAM_ARM_feature_spoof`, built from source at install, reports device features DXVK lists as mandatory and Mali driver does not expose, then removes them again from device creation; self-check through `vulkaninfo` when present; `STEAM_ARM_VK_SPOOF_DISABLE=1` turns it off per title, `STEAM_ARM_VK_SPOOF_DEBUG=1` prints its decisions
- Launcher enables GLX copy and Vulkan layer only when their components were selected
- Launcher registers client's arm64 overlay Vulkan layer once, for titles profiled `overlay=vulkan`, and removes any second registration of it, which hangs Vulkan titles at start
- `map-count` component: `vm.max_map_count = 2147483642` in `/etc/sysctl.d/zz-steam-arm.conf`, value Proton expects; `zz-` name so it is read after `/etc/sysctl.conf`; value from before setup kept in file and restored on deselect or removal

## Remote Play
- Streaming runs package's x86-64 streaming client under system emulator, with software decoding
- `steam-arm-remoteplay` pins hardware decoding off and HEVC off in client's stored configuration, so host keeps to H.264 and software decoder; streaming client decodes through Vulkan Video, which Mali driver does not provide, and with hardware decoding advertised session can sit on launch screen and never finish negotiating
- Launcher applies setting before every client start once account has signed in, so first stream already runs with it; `--check` reports without changing anything; Remote Play section of `steam-arm-config` shows state and applies it
- Game window in background on host renders nothing new, so stream shows one frame and takes no input; keep game in foreground on host

## Controllers
- `pad-hidraw` component: Valve's controller rules from `steam-devices` (`/etc/udev/rules.d/60-steam-input.rules`), unless system package already provides them; plus `/etc/udev/rules.d/60-steam-arm-gamepad-hidraw.rules` for 241 pads from kernel `xpad` table that Valve's list lacks, matched on vendor and product; Sony and Nintendo hidraw devices matched by kernel pad driver (`hid-playstation`, `hid-sony`, `hid-nintendo`), so keyboards and mice of those makers stay out, with whole vendor as fallback on kernel without that driver module; client reads pads directly for rumble and battery level
- `xpad-dedup` component: `/etc/udev/rules.d/71-steam-arm-xpad-dedup.rules` unbinds driver from headset interface some third-party Xbox 360 style pads expose, so one pad is one joystick and two-player game does not hand player 2 copy of player 1; `steam-arm-xpad-dedup` does same for pads already connected
- `pad-xbox` component, off by default: `steam-arm-pad-xbox.service` presents XInput pads from other makers as Xbox 360 pads through `uinput`; off because client's own Steam Input re-identifies pads, and launcher pauses service while client runs, through sudo rule that exists only with this component and is checked with `visudo` before it goes live

## Emulation
- FEX-Emu installed from project's PPA: build matching CPU (`fex-emu-armv8.0`, `-armv8.2` or `-armv8.4`, same rule as FEX installer), 32-bit and 64-bit binfmt
- `steam-arm-fex-binfmt.service`: FEX owns x86 execution persistently; box64 and box32 binfmt registrations off while it runs
- x86-64 root filesystem: Ubuntu 24.04, prepared by installer at `/opt/fex-rootfs/Ubuntu_24_04`; about 2 GB
- Client's runtime container built through `bubblewrap`

## Installer
- One script: `steam-arm-install.sh`; GitHub source also builds `.deb` package that installs command `steam-arm-setup` and installer script; nothing downloads at package install; `steam-arm-setup --detect`, `--list` and `--help` run without root; package removal prints how to remove installed client
- `sudo bash steam-arm-install.sh` installs core (host packages, root filesystem and graphics provider, client package, launcher, settings menu) and offers optional components: `glx-lax`, `vk-spoof`, `gpu-in-emulation`, `shader-cache`, `physx-skip`, `map-count`, `xpad-dedup`, `pad-hidraw`, `pad-xbox`, `desktop`, `desktop-mode`, `icon-bigpicture`, `icon-desktop`, `tray`, `kde-input-prompt`, `page-size`; `pad-xbox`, `shader-cache` and `kde-input-prompt` off by default, `vk-spoof`, `gpu-in-emulation` and `glx-lax` per GPU family, rest on
- Component choice through settings menu, desktop dialog (zenity) when started with no options and no controlling terminal in graphical session, or `--select a,b`, `--skip a,b`, `--defaults`, `--keep`; `--list` prints components, `--help` marks defaults of this system
- Re-running refreshes installed files, and component deselected on re-run is removed again
- Installed games kept: install, re-run, component changes and package upgrade leave game library (`steamapps`), sign-in and settings untouched; only client's program folder is replaced, and only when missing or not ARM64
- Settings file `/etc/steam-arm/steam-arm.conf`: `ARMHOME_DIR`, `GAMEUSER`, `COMPONENTS_ON`, `COMPONENTS_OFF`, `COMPONENTS_USER_SET`, `COMPONENTS_FAMILY`, `GPU_FAMILY`, `GPU_FAMILY_SET`, `GFX_DEFAULT`, `VERSION`, `ACCOUNT_CREATED`, `LINGER_SET`, `FSTAB_ADDED`, `RFS_CREATED`, `PROVIDER_CUSTOM_SHA256`, `PROVIDER_CUSTOM_FILE`, `ARMHOME_FOREIGN`; edited in place, other lines kept
- GPU components (`vk-spoof`, `gpu-in-emulation`, `glx-lax`) follow GPU family change between runs, except those set by hand (`COMPONENTS_USER_SET`); `--defaults` clears that record
- Install, Update / Repair and component changes refuse while Steam ARM runs for game account (`Steam is running for '<user>'`); second setup run during install or removal refused (lock)
- Client folder marker `.steam-arm-client`, written from 2.0 on, Update / Repair included, only into folder that was new, empty, already marked or client folder of earlier Steam ARM install (1.2: default folder name only); folder that held other files recorded as `ARMHOME_FOREIGN=1`, never marked on later runs and kept by `--remove` with message; folder with `steamapps` or `ubuntu12_32` at top level refused as other Steam install
- Unfinished x86 root filesystem extraction from earlier run discarded, or extracted again from downloaded `.sqsh`
- `/dev/shm` line in `/etc/fstab` added only when nothing else mounts `/dev/shm` at boot (no own line, no `dev-shm.mount` unit), recorded as `FSTAB_ADDED=1`
- `desktop` component: application menu entry "Steam ARM", right-click actions open either interface; window rule gives desktop interface windows title bar, and KWin reloads its rules so it applies at once
- `desktop-mode` component: second menu entry, "Steam ARM (Desktop mode)", found by searching "desktop" or "sign in"
- `icon-bigpicture` and `icon-desktop` components: desktop icon for either entry, each chosen on its own; neither selected places none
- `tray` component: tray helper above; deselecting it removes helper and its autostart entry and stops it
- Menu icons made at install from client's own `steam_tray.ico`: dark, grainy green disc with small squares of vivid colour, chartreuse logo for Big Picture and bone logo for desktop mode; fixed seeds, so every install draws same icons; nothing bundled
- Before client's first start, `steam_tray.ico` does not exist yet: setup draws disc without logo and marks it as placeholder; launcher redraws icons with logo once client has downloaded that file
- Page size check before anything installs: emulation needs 4K pages; 16K or 64K kernel stops setup with fix for that system, `STEAM_ARM_IGNORE_PAGESIZE=1` to skip
- CPU check before any package change: client needs Armv8.1 LSE atomics (`atomics` in first CPU's `Features` line); Armv8.0 CPU stops setup, Install / Setup screen and launcher with message naming [steam-for-linux #13288](https://github.com/ValveSoftware/steam-for-linux/issues/13288), `STEAM_ARM_ALLOW_ARMV80=1` to skip
- Setup and removal banners name page size, for example `Page size: 16K (board default); x86 emulation needs 4K, page-size component switches it`
- `page-size` component: on Raspberry Pi with 16K page kernel, adds `kernel=kernel8.img` to firmware `config.txt` in marked block, keeps backup, and asks for reboot and second run; deselecting removes block again; listed only on Raspberry Pi 5 class boards, on other Raspberry Pi with page size other than 4K, or while its block is in place
- `kde-input-prompt` component, off by default: on KDE Plasma (Wayland), pre-authorises input from X11 programs in KDE's permission store (`kde-authorized`, `remote-desktop`, empty app id), so controller that drives desktop raises no "Remote control requested" prompt; trade-off: every X11 program may then send input without asking; value it replaces saved and put back when part is turned off or on `--remove`; applied inside desktop session (at next Steam ARM start when no session runs); listed only where KDE Plasma's Wayland compositor is installed or its setting is in place; setup, `--detect` and Information print one-line hint in KDE Plasma Wayland session
- Header names no board; same script runs on its own or from units, TTY gated, `NO_COLOR` honoured
- Security: files in game account's home written as that account; client folder path validated; account named in settings file must exist; Valve's FEX tool files, settings, profiles and `config.txt` edited through new file renamed over old one; temporary files made with `mktemp` and removed on exit; client package and driver archive checked against checksums
- Uninstaller: `--remove` removes launcher, helpers, settings menu, installer copy, menu and desktop entries, icons, controller rules, services, sudo rule, window rule, apt hook, setup logs and `/etc/steam-arm` (game profiles saved to `/var/backups/steam-arm-titles-<date>.conf` first), and restores `vm.max_map_count`, root filesystem's Mesa files and package tools, Raspberry Pi `config.txt` (backup then deleted), KDE input permission (when `kde-input-prompt` set it), Valve's FEX tool files and Valve's streaming client; turns lingering off only when setup turned it on; removes `graphics_provider.json` and `~/.fex-emu/Config.json` only while unchanged since setup; removes `/dev/shm` line from `/etc/fstab` only when setup added it; keeps client folder with games unless deletion is confirmed by typing `DELETE`, and deletes it only when it holds marker `.steam-arm-client` (older install without marker: folder kept, `rm -rf` line printed); keeps root filesystem, distribution packages, account groups, `/dev/shm` line setup did not add (listed as kept) and account setup created (prints `sudo userdel -r <name>`), and prints `apt remove` line for packages nothing else needs; refuses while client runs or another setup run is in progress
- `--replace-other`: retires other variant of this installer before setup into two archives: system files to `/var/backups/steam-arm-replaced-<date>.tar`, files from its account's home to `/var/backups/steam-arm-replaced-<date>-<user>.tar`, owned by that account; restore commands printed (`sudo tar -xpf <archive> -C /`, `sudo -u <user> tar -xpf <archive> -C /`); client folder and account of other variant stay in use unless `ARMHOME_DIR`, `GAMEUSER` or settings file name others
- `--detect-other`: prints whether other variant of this installer is present, status 0 when present; needs no root. Install in `steam-arm-config` asks before it replaces other variant (Replace or Back)
- `--remove --purge`: also deletes client folder with every installed game (marker required) and root filesystem, after typed confirmation; root filesystem only when setup downloaded it and other variant of this installer is not installed; without terminal nothing is deleted

## Requirements
- ARM64 system; Vulkan driver for Windows titles, native OpenGL titles run without one; Debian or Ubuntu family distribution, since installer uses `apt`
- Mesa graphics stack for `glx-lax`; `vk-spoof` and `gpu-in-emulation` written for Mali (Panfrost and PanVK), on by default on Mali GPUs only
- Ubuntu family system for FEX PPA; other systems need FEX from another source
- No hardcoded GPU render node or card index; GPU family detection reads every render node

## Compatibility
- Test device: RK3588 board with Mali-G610 GPU
- `COMPATIBILITY.md` records GPU families and their defaults, per device class and per driver, and which title classes do not run on Mali
